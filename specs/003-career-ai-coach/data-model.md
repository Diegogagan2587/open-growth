# Data Model: Career AI Coach

## Reporting::Conversation

Existing table/model extended with domain-aware scope.

| Attribute | Type | Rules |
|---|---|---|
| `account_id` | bigint | Required; all context queries use this account. |
| `account_membership_id` | bigint | Required; must belong to `account_id`; controls access and quota. |
| `title` | string | Required; user-visible conversation title. |
| `date_from`, `date_to` | date | Required; immutable after creation and valid for the existing maximum range. |
| `analysis_domain` | string | Required; canonical values `financial` or `career`; immutable after creation. |
| `career_context` | JSON/JSONB | Career-only optional context selection, defaulting to applications/statuses/events; empty for financial conversations. |
| `turns_count` | integer | Existing counter cache. |

The migration must use a safe default for existing rows (`financial`), backfill/validate existing data, and add a database check constraint or model/database-compatible validation for supported domains where practical. Existing financial conversations must remain readable and behaviorally unchanged.

Relationships remain `Account has_many Reporting::Conversation`, `AccountMembership has_many Reporting::Conversation`, and `Reporting::Conversation has_many Reporting::Turn`/`UsageEvent`.

## Career analysis context

This is a request-scoped serialized snapshot, not a new persisted record. It is generated by a reporting domain object from the conversation’s account and immutable date range; it is not implemented as a business-logic service.

Default data:

- `Career::JobApplication`: id, company/role, status, priority, source, location/remote type, fit score where available, found/applied dates, and relevant timestamps.
- `Career::Event`: id, application id, event type, occurred-at timestamp, and safe metadata needed for timeline analysis.
- Derived metrics: application count, current status counts, stage progression/conversion where measurable, elapsed stage timing, stalled candidates, and data-quality limitations.

Optional data, only when selected by the user:

- `Career::Profile` and explicitly permitted profile fields.
- Application-linked notes/documents, tasks, and meetings, serialized with identifiers and dates/content needed for analysis.

All relations must be account-scoped. Application-linked records must be reachable through the selected account’s applications and must not broaden scope. Snapshot output must include low-data/incomplete-data indicators and never invent missing metrics.

## Career pattern finding

Provider output concept, represented in the structured response rather than necessarily persisted as a separate table:

- finding type: metric, bottleneck, hypothesis, limitation
- observed evidence and record identifiers
- confidence/uncertainty wording
- competing explanations when applicable

## Career recommendation

Provider output concept:

- priority
- concrete action or measurable experiment
- intended outcome
- evidence or assumption
- informational/read-only disclaimer

## Lifecycle and invariants

1. A conversation is created with one domain and fixed scope.
2. Turns are queued and processed through the existing reporting pipeline.
3. Follow-up turns reuse the conversation’s domain and context selection.
4. Financial and career records are never mixed unless an explicitly supported cross-domain mode is later added; this feature does not add that mode.
5. Deleting a conversation retains usage metadata according to existing behavior.
